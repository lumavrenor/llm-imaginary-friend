# llm-imaginary-friend（LLM イマジナリーフレンド）

5人のイマジナリーフレンドと話すチャット型アプリ。5人はユーザーの心の一面から生まれた女の子たちで、世界観はゆるい日常ものの4コマ漫画。
性格も考え方も違い、ユーザーへの返答だけでなく、女の子どうしで笑ったり、ケンカしたり、仲直りしたりする。
心の中の町（イマジナリーランド）で暮らしていて、ユーザーのいない間の出来事や、前の会話を覚えている。
6人目の「イオ」は、接続中の LLM そのもの。町はずれの電気室から、自分が動いているモデルの調子を話す。

個人の趣味プロジェクトです。ご質問・ご要望への対応はしておりません。
ただし、権利・規約上の問題や不具合のご指摘は、GitHub の Issue で受け付けています。

実装はすべて Python です。3D 表示は [Ursina](https://www.ursinaengine.org/) エンジンで、キャラクターのモデルと動きは、
以前作った24時間ラジオ [llm-radio-daemon](https://github.com/lumavrenor/llm-radio-daemon) から流用しています（コードで作る3Dモデル。外部のモデルファイルは使っていない）。
LLM・音声合成・検索のどれも、自分の PC とキー不要の公開 API だけで動く（課金なし）。

## 本プロジェクトの位置づけ

これは実用ソフトウェアではありません。プログラマーが手元で遊ぶための実験的なソフトウェアです。
主眼は「自分の PC のローカル LLM だけで、性格の違う6人がどこまで“生きている”ように話せるか」を試す点にあります。
挙手・発話者選び・喜怒哀楽・好感度・町の出来事・個人記憶といった仕掛けは、どれも小さめのモデルでも破綻しにくくするための工夫です。

## LLM が生成する内容について（重要）

キャラクターのセリフ・町の出来事・記憶メモは、すべてローカル LLM がその場で生成したフィクションです。
実在の人物・団体とは関係なく、専門家による確認もしていません。

- キャラクターは、ネット検索・ニュース・天気予報の結果をもとに話すことがありますが、要約や受け答えの中で事実と違うことを、自信のある口調で言うことがあります
- 本ソフトには、生成されたセリフを読み上げ前に検査する NG ワードのフィルタはありません。LLM が不適切な内容を出力する可能性を、ゼロにはできません（これは実装の不足ではなく、現在の生成 AI 技術そのものの限界です）
- 「話し相手」の形をしていますが、相談窓口やカウンセリングの代わりにはなりません。**医療・法律・金融・安全に関わる内容を、本物の助言として扱って行動しないでください**
- 本ソフトの出力によって生じた損害について、作者は責任を負いません

## 必要なもの

- Windows 11（Linux・macOS でも `go.sh` で動く作りだが、作者が確かめているのは Windows のみ）
- Python 3.11 以上（作者は 3.14 で確認）
- OpenAI 互換の LLM サーバ（SGLang / Ollama など）。作者は gemma-4-31B（NVFP4）と qwen3.8:27b で確認している。
  キャラとして自然に喋るのは gemma-4-31B のほうが上手だった（qwen3.8:27b は内容は合っていても言葉づかいが崩れることが多い）。
  vLLM 用の設定（`engine = "vllm"`）もあるが、作者は試していない。
  6人分の挙手を並列に投げるので、並列リクエストに強いサーバ（SGLang）のほうが返事が早い
- [VOICEVOX](https://voicevox.hiroshiba.jp/)（日本語版の声。英語版は不要）
- ネット接続（検索・ニュース・天気を使う場合。どれもキーは要らない。切っても動く）

## 機能

- 画面: Ursina（3D キャラ5人＋6人目・会話ログ・入力欄）
- LLM: OpenAI 互換サーバ（SGLang / Ollama など）
- 音声: VOICEVOX ENGINE
- 検索: Wikipedia ＋ Google ニュースの RSS 検索（既定。どちらもキー不要）/ Brave Search API / SearXNG。ユーザーへ最初に答える分身と、話し込み中の各ラウンドの最初の話者がツールコーリングで使う
- ニュース: RSS（NHK・Yahoo!・GIGAZINE など）を裏で読み、分身がときどき「さっきネットで見かけた」話題を自分から持ち込む
- 天気予報: Open-Meteo（キー不要）。今の空模様を会話の状況に入れ、ときどき分身が「さっき天気予報を見たら」と話題に出す

## 起動

1. LLM サーバ（SGLang なら `127.0.0.1:30000`）と VOICEVOX（`127.0.0.1:50021`）を起動しておく。
   SGLang の起動のしかたは下の「[LLM サーバ（SGLang）の設定](#llm-サーバsglangの設定)」
2. `go.bat`（Git Bash・Linux・macOS なら `./go.sh`）

入力欄に日本語で打って Enter。マウスホイールでログをさかのぼれる。
入力欄はふつうのテキスト欄と同じように編集できる:

- 範囲選択: Shift+←→ / Shift+Home/End / Ctrl+A / マウスのドラッグ / Shift+クリック / ダブルクリック（単語）/ トリプルクリック（全体）
- 単語単位: Ctrl+←→ で移動、Ctrl+BackSpace / Ctrl+Delete で削除
- Ctrl+C / Ctrl+X / Ctrl+V（または Shift+Insert）。選択が無いときのコピー・切り取りは全文。改行を含む文は1行にして貼り付ける
- Ctrl+Z で元に戻す、Ctrl+Y / Ctrl+Shift+Z でやり直す

会話ログのメッセージもコピーできる:

- クリックで1件選ぶ。ドラッグや Shift+クリックで続けて何件か選ぶ
- Ctrl+C でコピー（1件なら本文だけ、複数なら「名前: 本文」を1行ずつ）。右クリックはその1件をすぐコピー
- Esc か、ログの空いたところをクリックすると選択を解く

| オプション | 意味 |
|---|---|
| `--cli` | ウィンドウを開かず標準入出力で会話（動作確認用） |
| `--no-audio` | 音を出さない（ログと口パクは進む） |
| `--no-idle` | 自発的な雑談と起動時の挨拶を止める |
| `--no-search` | ネット検索ツールを使わない |
| `--no-news` | 分身が自分からニュースの話題を持ち込まない |
| `--no-weather` | 天気予報を取らない（天気に触れない） |
| `--config PATH` | 設定ファイル（既定 `config.toml`） |

### 英語版（English edition）

`go.bat en`（bash なら `./go.sh en`）で、英語で話す版が起動する。英語の説明は [README.md](README.md)。

- 設定は `config.en.toml`（`[locale] lang = "en"`）。DB も `data/imaginary_friend_en.db` に分けてあるので、日本語の会話や記憶とは混ざらない
- 声は VOICEVOX の代わりに Kokoro-82M（Apache-2.0）を CPU で動かす。VOICEVOX は要らない
- 初回だけ、追加の依存（`requirements-en.txt` と spaCy の `en_core_web_sm`）を入れ、モデル一式（約340MB）を `kokoro_models/` に取ってくる
- 5人と6人目の見た目は日本語版と同じ。性格・話し方・例文・つなぎの一言は英語で書き直し、声は Kokoro の英語ボイスの配合で作った（`[[cast]] kokoro_voice`）。
  気持ちごとに声を変えたいときは `kokoro_emotions = { sad = [...] }`（書いていない気持ちは話速だけ変える）
- 名前の読みは `lexicon.en.txt` で固定している（Nene は「ネネ」、Io は「イオ」）。辞書に無い語は推定で読み、ログに WARNING を1回出す
- 声だけ試す: `.venv\Scripts\python -m imaginary_friend.main --config config.en.toml --voice-test out`（各キャラの例文を `out/` に WAV で書く。LLM は使わない）
- プロンプトは日本語版を残したまま、英語版を隣に足して `[locale] lang` で選んでいる（`imaginary_friend/language.py` の `pick(ja=..., en=...)`）。日本語版の文面は変えていない
- 英語版では、気持ちのタグは `[happy]` `[cheerful]` `[angry]` `[sad]` `[surprised]` `[shy]` `[neutral]`、記憶と町の出来事の近さは2文字ではなく語の重なりで測る
- DB を消すときは `reset.bat --config config.en.toml`

### データベースを消す

`reset.bat`（bash なら `./reset.sh`）で、会話ログ・記憶・気分と関係の DB を消す。消す前に一覧を出して確認する。
アプリを閉じてから実行する。次に起動したとき空の DB が作られる。

| オプション | 意味 |
|---|---|
| （なし） | `config.toml` の `[store] path` の DB だけ消す |
| `--all` | `data/` の `*.db` をすべて消す（昔の DB も消える） |
| `--config PATH` | `[store] path` をこの設定ファイルから読む |
| `-y` | 確認しないで消す |

## LLM サーバ（SGLang）の設定

**セットアップは、コーディングエージェント（Claude Code や Codex など）に任せることをおすすめします。**
SGLang は版ごとに引数や対応モデルがよく変わり、GPU の枚数・VRAM・モデルの量子化の組み合わせで、必要な設定も落ちる場所も変わります。
この節と、自分の GPU・使いたいモデル・SGLang の版をエージェントに伝えて、起動スクリプトを作ってもらうのが早道です。
下の起動例は作者の環境のもので、そのまま動くとは限りません。エージェントに渡す下敷きとして使ってください。

手間をかけずに試すだけなら、Ollama でも動きます（`[llm] profile = "ollama"`）。並列リクエストが遅いぶん、返事は遅くなります。

### 本アプリから見た要件

- OpenAI 互換 API（`/v1/chat/completions`）が、`config.toml` の `[llm.sglang] host`（既定 `http://127.0.0.1:30000`）で待ち受けていること。
  `--served-model-name` は何でもよい（`model` を省略すると `/v1/models` の先頭を使う）。6人目のイオは `/get_model_info` の重みのパスから本当のモデル名を取るので、別名にしても困らない
- `--context-length` は 8192 以上。`[talk] history_chars = 3000` はこの長さに合わせてある。短くするなら `history_chars` も減らす
- 1ラウンドで6人分の挙手を並列に投げ、そのあと話者の返答・先読み・記憶メモの要約が続く。`--max-running-requests` は 8 程度で足りる
- 検索を使うなら `--tool-call-parser` が要る（Gemma 4 なら `gemma4`、qwen3.8 なら `qwen3_coder`）。付けられないモデルでは `--no-search` で起動する
- 思考するモデルなら `--reasoning-parser` で思考部分を分ける（Gemma 4 なら `gemma4`）
- 挙手は JSON スキーマ指定の structured output。`--constrained-json-disable-any-whitespace` を付けると、空白を出し続けて止まらない失敗を防げる
- radix cache は有効のままにする（プロンプトの先頭が全員共通なので、prefill を省ける）

### 作者の環境での起動例

GPU 3枚（パイプライン並列）・Gemma 4 31B の NVFP4 量子化（[RedHatAI/gemma-4-31B-it-NVFP4](https://huggingface.co/RedHatAI/gemma-4-31B-it-NVFP4)）・SGLang 0.5.21・WSL2 の Ubuntu。

```bash
export CUDA_VISIBLE_DEVICES=1,2,0              # 画面出力に使っている GPU を最後に
export SGLANG_PP_LAYER_PARTITION=17,26,17      # 60層の割り振り（先頭は埋め込み、末尾は lm_head を持つので少なめ）
export PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True
export TOKENIZERS_PARALLELISM=false

python -m sglang.launch_server \
  --model-path /path/to/gemma-4-31B-it-NVFP4 --served-model-name npc \
  --tp-size 1 --pp-size 3 \
  --context-length 8192 --mem-fraction-static 0.93 --kv-cache-dtype bfloat16 \
  --max-running-requests 8 --max-queued-requests 32 \
  --cuda-graph-max-bs-decode 8 --disable-prefill-cuda-graph --enable-cache-report \
  --reasoning-parser gemma4 --tool-call-parser gemma4 \
  --constrained-json-disable-any-whitespace --skip-server-warmup \
  --host 127.0.0.1 --port 30000
```

この構成で、1件なら 17 tok/s、5件同時なら各 9〜12 tok/s ほど出ている。GPU 1枚に収まるモデルなら、`--pp-size` と `SGLANG_PP_LAYER_PARTITION` は要らない。

作者の環境で引っかかったところ（エージェントに伝えると話が早い）:

- `--kv-cache-dtype bfloat16`: Gemma 4 は triton attention で動き、FP8 の KV キャッシュだと落ちる
- `--skip-server-warmup`: RedHatAI 版は画像エンコーダも FP4 で、SGLang 0.5.21 では画像入りのリクエストを1回通すと、以後の返答がすべて `<pad>` になる（サーバの再起動が要る）。
  本アプリは画像を送らないが、起動時のウォームアップが画像入りなので飛ばしている
- Gemma 4 の KV は重い（全層 attention の層で 8k 文脈 1件 約 1.1GB）。NVIDIA 公式の NVFP4 版は attention を BF16 のまま残していて精度は良いが、重みが大きく、GPU 3枚でも KV が 8k 文脈 1件分も取れなかった
- SGLang 0.5.21 には、パイプライン並列で各段が全層ぶんの KV を確保してしまう不具合と、compressed-tensors 形式の NVFP4（RedHatAI 版）の読み込みの不具合があり、
  作者は手元でパッチを当てて動かしている（パッチは本リポジトリに含めていない）。同じ構成で動かすなら、症状をエージェントに伝えて直してもらってください

## 設定（config.toml）

- `[llm] profile = "auto"` は `[llm.<名前>]` を書いた順に試し、最初に応答したサーバを使う。`model` を省略すると `/v1/models` の先頭を使う
- `[user] name` は分身たちからの呼び名。「あなた」のままだと、キャラへの「あなたは〜です」と混ざって分身どうしでも「あなた」と呼び合うので、名前にしておく
- `[[cast]]` が5人の定義（性格 `desc`、話し方の例 `examples`、見た目、VOICEVOX の声）。`examples` は口調の手本で、小さいモデルほど効く。
  `voicevox_emotions = { "哀" = "泣き" }` のように、気持ちごとに VOICEVOX のスタイルを割り当てられる（書いていない気持ちは声の高さ・抑揚・速さで表す）
- `[affinity]` が「ふだんの」好感度マトリクス。低い相手の発言には言い返しやすくなる。会話の中の感情で今日の値が上下する
- `[drama]` で喜怒哀楽・今日の気分・演出の有効／無効と、演出を仕掛ける確率を変える（下の「喜怒哀楽と演出」）
- `[meta]` / `[meta.cast]` が6人目「モデルの子」（下の「6人目」）。比較試験では `enabled = false` にする
- `[store] path` は会話ログ・記憶・気分と関係を保存する DB
- `[talk]` で返答人数・1回の発言の長さ（`max_chars` / `max_sentences`）・LLM に見せる会話ログの長さ（`history_lines`）・話し込みの長さ（`session_min_sec` / `session_max_sec`）・雑談の間隔を変える
- `[search]` で検索の有効／無効と検索先（`backend`。複数書くと並列に引いて「事典」「ニュース」に分けて渡す）、話し込み中に自分から調べてよい回数（`max_per_session`）、話していない子の裏での調べもの（`background` ほか）を選ぶ。`[[cast]] search_line` は、分身が一言も言わずに検索を始めたときに代わりに言うつなぎの一言
- `[news]` で、分身が持ち込むニュースの RSS（`feeds`）、出す確率（起動時の挨拶 `start_chance`・雑談 `idle_chance`・話し込みの後半 `talk_chance`）、話題にしない語（`skip_words`）を変える
- `[weather]` で天気予報の場所（`location_name` / `latitude` / `longitude`）、今の空模様を状況に入れるか（`in_situation`）、自分から話題に出す確率（`start_chance` / `idle_chance` / `talk_chance`）と間隔（`min_gap_min`）を変える。書かなければ天気には触れない
- `[memory]` で個人記憶の有効／無効、思い出す件数、記憶メモを書く区切りの長さを変える
- `[display] ime_aware` は IME 変換中の文字を入力欄の中に出すか（false なら OS の変換ウィンドウ）
- `[display] layout_jitter` は立ち位置のずれ。みんなは見ている側を囲む円弧に立ち、起動ごとに乱数で少しずつ位置と向きが変わる（0 で整列）

## しくみ

```
UI スレッド (Ursina)  ←─ イベントキュー ─┬─ brain スレッド（挙手 → 発話 → 合成）
   描画・入力欄・ログ                    └─ オーディオコールバック（再生開始の通知）
```

1ラウンドの流れ（`imaginary_friend/brain.py`）:

1. **挙手フェーズ**: 5人へ並列に「言いたいこと・立場・喋りたい度合い」を短い JSON で聞く
2. 上位の1人が発話。ストリームを文単位に切り、VOICEVOX で先行合成して1本の再生キューへ積む
3. 2人目は1人目の発言を見たうえで発話する。1人目と仲が悪いキャラほど選ばれやすい

ユーザーの発言に最初に答える分身と、話し込み中の各ラウンドの最初の話者（`max_per_session` 回まで）に、検索ツール `web_search` を渡す。
分身がツールを呼んだら、「ちょっと調べるね」の再生中に検索し、結果を踏まえて続きを話す。
検索結果の全文は、調べた本人の個人記憶にだけ残る。ほかの分身は、本人が口で言った範囲（会話ログ）しか知らない。

**裏での調べもの**（`[search] background`）: 挙手の JSON で「調べておきたいこと（`check`）」も聞き、その回の最初の話者以外の子は、
ほかの子が話している間に裏で検索しておく。挙手の質問に1項目足すだけなので、LLM へのリクエストは増えない。
結果は調べた本人の個人記憶にだけ入り、自分の番が来たら「さっき調べたんだけど」と使える（間に合わなければ最大5秒待つ）。
1ラウンドに `background_per_round` 人まで、ユーザーの発言から次の発言までに `background_per_session` 回まで。
同じ検索語は引き直さず、最初の話者が検索ツールを持つラウンドでは、話者と同じことは裏で調べない。
調べ終わった子は、次の話者に選ばれやすくなる。
検索ツールを持つ話者が挙手で `check` を出していたのにツールを呼ばなかったときは、「ちょっと調べてみるね」でつないで `check` の語で代わりに調べる
（小さいモデルは「知ってる？」と聞かれても、調べずに「誰だろう」で済ませがちなため）。

**ニュース**（`imaginary_friend/news.py`）: `[news] feeds` の RSS を裏で定期的に読む。起動時の挨拶・自発的な雑談・話し込みの後半（1回まで）で、
ときどき1人が「さっきネットで見かけたニュース」を自分から切り出す。ユウが「最近なにかニュースあった？」と聞いたときも、1人に見かけたニュースを渡して答えさせる（名前を呼ばれた子がいればその子）。見出しと概要はその子のプロンプトと個人記憶にだけ入る。
説明文の無い記事は、話題に出す直前に記事ページの概要（meta description）を読みに行く。一度出したネタは DB に記録して、再起動してもくり返さない。

**天気予報**（`imaginary_friend/weather.py`）: `[weather]` の緯度経度で Open-Meteo から、今の天気・気温と今日・明日の予報を裏で取る（30分ごと）。
今の空模様は全員共通の「今の状況」に1行入り、ユウの発言が天気・傘・明日などに触れたときは予報も入る。
起動時の挨拶（ニュースより先に試す）・自発的な雑談・話し込みの後半で、ときどき1人が「さっき天気予報を見たら」と自分から切り出す（予報はその子にだけ渡す。夕方からは明日の予報が中心）。
取れなかったとき・3時間以上古いときは天気に触れさせない。

**個人記憶**（`imaginary_friend/memory.py`）: 分身ごとに2種類の記憶を DB に持つ。

- 自分で調べたこと: 検索結果を要点に縮めたもの。調べた本人だけが覚えている
- 前の会話の記憶: 会話の区切り（話し込みの終わり・ユーザーの次の発言）で、各分身が自分の視点で書く短いメモ。
  自分で調べた事実は具体的に、ほかの分身の話は聞いた範囲でざっくり書くので、同じ会話でも覚え方がキャラごとに違う

話すときは、今の話題に近い自分の記憶（`[memory] facts_in_prompt` / `notes_in_prompt` 件）を、キャラ固有部分のプロンプトに入れる。
近さは漢字・カタカナ・英数字を含む2文字の重なりで測る（埋め込みモデルは使っていない）。再起動しても残る。

ユーザーが発言したあとは「話し込み」になり、分身どうしが3〜5分（`session_min_sec`〜`session_max_sec`）しゃべり続ける。
「おやすみ」「またね」「行ってきます」のような切り上げのあいさつには返事だけをして、話し込みも、次の発言までの自発的な雑談もしない。
再生待ちが `lookahead_sec` 秒を切るたびに次のラウンドを作るので、声は途切れず、先に作りすぎもしない。
長く話しても堂々巡りにならないよう、ラウンドの最初の話者には「具体例を出す」「反論する」などの進め方を1つ渡す。
ユーザーが発言すると、まだ再生していないセリフはその場で捨てて（再生中の1文だけは言い切る）、そちらへの返答を始める。
起動時の挨拶のあと、ユーザーが黙っている間は、タイマーで同じラウンドを回す（`max_auto_rounds` 回まで。話し込みのあとは回さない）。

プロンプトは「共通部分（設定・全員の人物紹介・会話ログ）→ キャラ固有部分」の順で、並列リクエストの先頭が一致する。

### 6人目「モデルの子」（`imaginary_friend/meta.py`）

接続中の LLM そのものが、町はずれの電気室から話す子（名前は「イオ」）。

- どのモデルで動いていても同じ1人。名前・見た目・声は `[meta.cast]` に1つだけ書き、記憶・好感度・気分の id も `llm` の1つ。
  モデル名は接続先から自動で取る（SGLang は `/get_model_info` の重みのパス、Ollama は model 名、vLLM は `root`（未確認）。取れなければ `[llm.<名前>] display_model`）
- 起動時に `meta_runs` テーブル（モデル名ごとの動いた記録）と比べ、「初めて動いた」「前回は別のモデルだった」「このモデルは初めて」「前に動いていたのは3日前」を本人の材料にする
- 本人のプロンプトにだけ、本物の実行状況（モデル名・temperature・見えている会話の範囲・直前のセリフの生成秒数とトークン速度・失敗の回数・検索の残りなど）を「# いまの実行状況」として入れる。
  入れるのは、きっかけ（生成が遅かった・止まった・だれかが忘れた・ユウがしくみのことを聞いた・モデルが替わった・検索が尽きた）のあるラウンドと、`stats_chance` に当たったラウンドだけ
- ふだんは選ばれにくく（`appear_weight`）、きっかけがあると選ばれやすい（`cue_weight`）。続けて話すのは `max_streak` ラウンドまで
- 5人には、しくみの話は見せない（全員共通の紹介は `desc` だけ。本人だけが知っていることは `self_desc`）。町の出来事・ニュースには出ない
- 気分は実行状況から決める（止まったら「ぼんやり」、同じモデルの前回より速ければ「調子がいい」、モデルが替わったら「そわそわ」）
- 画面の名前欄には、呼び名の下に接続中のモデル名を出す（`show_model_name`）。長い名前はパラメータ数までに短くする（`gemma-4-31B-it-NVFP4-RedHat` → `gemma4-31B`）。固定したいときは `model_label`。
  本人のプロンプトには元の名前を渡し、声に出すときはこの短い名前で言うよう添えている（重みのファイル名をそのまま読み上げないように）

### 喜怒哀楽と演出（`imaginary_friend/drama.py`）

- **気持ちのタグ**: セリフの文頭に【喜】【楽】【怒】【哀】【驚】【照】【普通】を付けさせる（途中で変わればその文にも）。
  タグは読み上げずに外し、声と好感度・気分の変化に使う。タグが無い文は直前の気持ち（最初は挙手の JSON の `emotion`）を引き継ぐ
- **声**: `voicevox_emotions` にスタイルがあればその声（あんこもんの「よわよわ」など）、無ければ高さ・抑揚・速さを変える（`[voicevox] emotion_prosody`）
- **表情**（`display/expression.py`、既定はオフ）: 既定では3Dモデルに表情は付けない。`[display] expressions = true` にすると、眉の角度、目と口の形、ほおの赤み、涙、うつむき、頭上の漫符（♪ ムカッ しゅん… ！？ てれっ）。
  最後のセリフから14秒続き、そのあとは今日の気分の顔（眠い子は半目、落ちこんでいる子は困り眉）に戻る。
  モデルのメッシュは変えない（頭の子として板を足すだけ）が、可愛さが損なわれたので既定ではオフにしている
- **今日の気分**: 町の出来事（`town.py`）といっしょに、LLM がその日の各キャラの気分を作る。決まった表は持たない。
  同じ日なら再起動しても同じ（DB に保存）。決まるまでと、`[town] enabled = false` のときは全員「ふつう」
- **関係の変化**: 発言の気持ちと相手（名前を呼んだ子、いなければ直前に話した子）から、好感度と気分を動かす。
  怒りで好感度が基準より下がると「気まずい」状態になり、仲直りするまで残る。日をまたぐと好感度は基準へ半分戻る（DB の `state` テーブル）
- **演出**: 話し込みを起承転結に見立て、30〜50% あたりの「転」で口ゲンカ・ないしょ話の発覚・打ち明け話・ボケのどれか、
  65〜85% あたりの「結」で仲直り（気まずい2人がいれば優先）・励まし・笑いのどれかを仕掛ける。
  打ち明け話とないしょ話の発覚の材料は、町でのまだユウに話していない出来事。ないしょの出来事がその場にいなかった子に関係する話なら、その子が相手役になる。自発的な雑談でも `idle_beat_chance` の確率で仕掛ける。
  演出の指示は役のキャラ（リードと相手）のプロンプトにだけ入れ、その順に話させる。ほかの子は会話で聞いた範囲しか知らない

## 設計の前提と、公開時の注意

本ソフトは、自宅で自分が非商用で楽しむ個人利用を想定した設計です。そのため、以下は意図的に実装していません。

- 配信・ストリーミング出力機能、音声の録音・ファイル保存機能（`--voice-test` は声の調整用に例文を WAV にするだけ）

  出力は画面のログと音声になり、会話ログと記憶として手元の DB（`data/`）に残るだけです

## クレジット

音声合成には [VOICEVOX](https://voicevox.hiroshiba.jp/) を使用しています。
使用するキャラクターごとに利用規約が異なるため、必ず各キャラクターの利用規約を確認してください。

本ソフトは VOICEVOX および各キャラクターの公式・運営とは無関係の個人制作です。
5人と6人目（`[[cast]]` / `[meta.cast]`）は本ソフトのために作ったオリジナルの人格で、VOICEVOX の各キャラクター本人ではありません（声だけをお借りしています）。

`config.toml` の既定の声は以下のとおりです（`voicevox_speaker_name` を変えた場合はそれに合わせて書き換えること）:

```
VOICEVOX:春日部つむぎ
VOICEVOX:冥鳴ひまり
VOICEVOX:九州そら
VOICEVOX:四国めたん
VOICEVOX:あんこもん
VOICEVOX:ナースロボ＿タイプＴ
```

英語版の音声合成には [Kokoro-82M](https://huggingface.co/hexgrad/Kokoro-82M)（Apache-2.0）と
[misaki](https://github.com/hexgrad/misaki)（Apache-2.0）を、辞書に無い語の読みには [g2p_en](https://github.com/Kyubyong/g2p)（Apache-2.0）を使用しています。
misaki の英語 G2P が数字の読み上げに [num2words](https://github.com/savoirfairelinux/num2words)（LGPL-2.1）を利用しており、
本プロジェクトは非改変のライブラリとして import しているだけですが、念のためここに明記します。
Kokoro のモデル本体とボイスファイルはリポジトリに含めていません。初回起動時に `kokoro_models/` へ自動で取得されます
（取得元は Kokoro-82M を ONNX 形式に変換して配布している [kokoro-onnx](https://github.com/thewh1teagle/kokoro-onnx) の GitHub Releases。
`config.json` だけは Hugging Face の Kokoro-82M リポジトリから取得）。学習データの内訳は公式のモデルカードを参照してください。

- 3D 表示: [Ursina](https://www.ursinaengine.org/)（MIT）/ Panda3D（Modified BSD）
- 検索: [Wikipedia](https://ja.wikipedia.org/)（本文は [CC BY-SA 4.0](https://creativecommons.org/licenses/by-sa/4.0/)）と Google ニュースの RSS 検索。結果は LLM のプロンプトに入れるだけで、画面に転載はしない
- ニュース: 各社の RSS（`[news] feeds`）。見出しと概要を LLM に渡すだけで、記事の転載はしない
- 天気: [Open-Meteo](https://open-meteo.com/)（データは [CC BY 4.0](https://creativecommons.org/licenses/by/4.0/)。無料 API は非商用が対象）
